## 1. How to use this tracker

1. **One row per milestone.** The ID (`M<phase>.<n>`) is stable for the life of the programme and is the key in `milestones.csv`, in commit trailers (`Refs: M5.3`), in the evidence folder and in status reports.
2. **Acceptance is binary.** A milestone is `Done` only when every acceptance criterion in its row is evidenced. Partial acceptance is `Done with conditions` and needs a dated condition with an owner (section 4).
3. **Evidence lives in the repo.** Each accepted milestone gets a folder `docs/evidence/phase-NN/<ID>/` containing links to the CI run, k6 report, Grafana snapshot, UAT recording, audit-log export or signed PDF that proves the criteria. The register's evidence column is replaced by the link when the folder is created. Phase 10 already prescribes this layout (`docs/evidence/phase-10/realtime-rehearsal.md`).
4. **Owner is a role, not a person.** Names are assigned in the RACI kept by the Program Manager; the register stays valid through staffing changes.
5. **Dates do not move silently.** A forecast date different from the target date is reported in the weekly status (section 5); only the steering committee re-baselines a target date (section 6).

## 3. Phase gate definitions

Each phase ends with a **gate** `Gn` on its end date. A gate has _entry criteria_ (what must be true before the phase is allowed to start — checked at the phase kick-off) and _exit criteria_ (what must be evidenced to pass the gate). Exit criteria restate the phase's own success criteria and go-live checks at board level; the detailed checklists are section 11 (Production Readiness Checklist) and section 12 (Success Criteria Verification) of each phase plan.

### 3.1 Gate mechanics

| Aspect                    | Rule                                                                                                                                                                                                                                                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Forum                     | Phase exit review chaired by the Program Manager; decision by the **steering committee** (G1–G11, G13) or the **go/no-go board** (G12). Gate review is held on the gate Friday or the Monday after, never later than the successor's W1 Wednesday.                                                      |
| Evidence pack             | Phase lead circulates the pack 2 working days before: milestone evidence folders, section 12 evidence table, open risk register, open security findings, cost actuals vs range, handover note to successor phases.                                                                                      |
| Outcomes                  | **PASS**; **PASS WITH CONDITIONS** (each condition dated ≤ 4 weeks, with owner, tracked as a register row `G<n>-C<k>`); **FAIL** (re-review within 10 working days; successor phases start only on tasks that do not depend on the failed deliverables).                                                |
| Non-waivable              | No conditional pass with: an open Critical/High security finding on a component going to production; any ledger imbalance or unexplained reconciliation break older than 24 h (P5 onward); a regulatory/licensing gap for live customer money; missing rollback path for the phase's production change. |
| Independent deployability | Every gate confirms that the phase deployed to production dark (flags off) without customer-visible change and that its kill switches were exercised — the programme's first guiding principle.                                                                                                         |
| Sign-offs                 | Roles listed in each phase plan's section 11 sign the gate; the steering committee records the decision in the minutes and the PM updates the register.                                                                                                                                                 |

## 4. RAG status convention

### 4.1 Milestone status values

| Status                 | Meaning                                                                                                                 | Who sets it                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `Planned`              | Not started or started on plan; forecast = target                                                                       | PM (baseline)                              |
| `In progress`          | Work under way; forecast = target                                                                                       | Milestone owner                            |
| `At risk`              | Forecast still = target but an acceptance criterion depends on an unresolved item (external party, defect, environment) | Milestone owner, confirmed by PM           |
| `Slipped`              | Forecast > target date; new forecast recorded                                                                           | PM                                         |
| `Done`                 | Every acceptance criterion evidenced; evidence folder linked                                                            | PM after Friday acceptance review          |
| `Done with conditions` | Accepted with dated conditions (≤ 4 weeks); conditions tracked as `<ID>-C<k>` rows                                      | Steering committee or delegated phase lead |
| `Descoped`             | Removed or moved by approved change request; successor impact recorded                                                  | Steering committee                         |

### 4.2 RAG thresholds

RAG is reported per milestone, per phase and for the programme, on five dimensions. The phase RAG is the worst dimension; the programme RAG is the worst critical-path phase.

| Dimension           | Green                                                            | Amber                                                                                                                  | Red                                                                                                                                                       |
| ------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Schedule**        | Forecast ≤ target date                                           | Forecast slip ≤ 5 working days **and** within the phase's float ([Gantt §4.2](./01-gantt-chart.md#42-float-per-phase)) | Slip > 5 working days, or any slip on a zero-float phase that is not recovered within the same phase                                                      |
| **Scope & quality** | All acceptance criteria on track; test suites green              | One criterion at risk with a recovery plan; flaky suite quarantined ≤ 3 days                                           | Criterion unattainable without re-scope; open Critical/High security finding within 10 working days of a gate; ledger or reconciliation invariant failing |
| **Cost**            | Actuals and forecast inside the phase's USD range                | Forecast within +10 % of the high estimate                                                                             | Forecast > 10 % above the high estimate, or an unbudgeted vendor commitment                                                                               |
| **Risk**            | No High-impact risk with Likelihood High unmitigated             | A High-impact risk's trigger observed, mitigation in flight                                                            | Risk materialised and blocks a milestone; mitigation exhausted                                                                                            |
| **Dependencies**    | Inbound deliverables (other phases, vendors, regulators) on time | Inbound item late but inside float                                                                                     | Inbound item late beyond float or with no committed date                                                                                                  |

Programme-level overrides: a phase is **Red** regardless of other dimensions when (a) a regulator or sponsor bank objects to a live capability, (b) a P1/P2 production incident is open beyond its SLA, or (c) customer money is unreconciled for more than 24 h.

## 6. Escalation path

| Level  | Who                                                                                                                       | Raised when                                                                                                                                    | Time to decide                                                        | Can decide                                                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **L0** | Milestone owner / squad lead                                                                                              | Any blocker                                                                                                                                    | 2 working days                                                        | Task re-planning inside the milestone                                                                                                                           |
| **L1** | Program Manager + track leads                                                                                             | Milestone `At risk` or Amber on any dimension; cross-track resource conflict                                                                   | 3 working days (or next Monday status)                                | Move non-critical milestones within float; reallocate engineers between tracks for ≤ 2 weeks; trigger phase scope ladders already documented in the phase plans |
| **L2** | Solution Architect (technical), Head of Compliance / MLRO (regulatory), CFO delegate (cost), Security Engineer (security) | Interface change across phases; compliance or security acceptance in doubt; cost Amber                                                         | 2 working days                                                        | Architecture changes behind an ADR; compliance interpretations; risk acceptance for Medium findings                                                             |
| **L3** | Steering committee                                                                                                        | Any Red; any slip on a zero-float phase; gate FAIL; cost Red; change request touching scope of a success criterion                             | Next fortnightly meeting, or ad hoc within 48 h for critical-path Red | Re-baseline a target date (≤ 2 weeks on critical path); approve contractor surge or vendor spend inside the programme envelope; conditional gate passes         |
| **L4** | Executive sponsor → Board                                                                                                 | Go-live date (2027-12-10) or programme end (2028-06-30) at risk; total spend forecast above the approved envelope; regulatory enforcement risk | 5 working days                                                        | Move G12/G13; change the target-market list; budget increases                                                                                                   |

Immediate escalations (skip levels, page the on-call and notify L3 within 1 hour): ledger imbalance or double payout in production; sanctions-confirmed transfer completed; Critical security finding or suspected breach; regulator or sponsor-bank instruction to stop a capability; data-residency violation detected by the egress guard (P13).

Named external-dependency owners (watched at L1 every week): provider production onboarding — Program Manager (R4.1); COBAC sponsor bank — Program Manager / Compliance (R6.1); FIU registrations — Compliance Analyst (R8.3); app-store accounts and review — PM (R11.1, R11.14); pentest vendor slots — Security Engineer (R12.2); country licences — Compliance Analyst (R13.1).

## 7. CSV export and register maintenance

- [`docs/roadmap/milestones.csv`](./roadmap/milestones.csv) contains the same 97 rows in the same order with header `id,phase,milestone,target_date,owner,acceptance,status`. Text fields are double-quoted (RFC 4180); `target_date` is ISO-8601; `status` uses the values of section 4.1.
- The CSV is the import format for the PM tool and for the Phase 10 programme dashboard; the Markdown register above is regenerated from the same data so that both stay identical. When a status changes, update the CSV row first, then the Markdown row, in the same commit (`docs(roadmap): M5.3 done`).
- Adding a milestone requires a steering-committee change request; IDs are never reused. Conditions on conditional acceptances are appended as `M5.6-C1`-style rows with the condition's due date.
- A CI check (`node docs/roadmap/tools/check-docs.mjs`) validates links in this file and the Mermaid blocks in the Gantt; target dates must stay inside the phase windows of `schedule.json`.
